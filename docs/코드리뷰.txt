접근 가능한 저장소 `skerishKang/LoveBud` 기준으로 빠르게 전체 코드리뷰를 했습니다. 결론부터 말하면, **문서화와 구조 분리는 꽤 괜찮은데, 실제 운영 안정성과 보안 측면에서 바로 손봐야 할 문제들이 몇 개 보입니다.**

가장 중요한 이슈부터 적겠습니다.

1. **공개 트리 조회 시 비공개 메모리까지 섞여서 노출될 가능성**
   `tree-detail.js`의 GET은 트리가 `public`이면 접근을 허용한 뒤, 해당 트리의 메모리를 `queryMemories({ treeId })`로 전부 가져옵니다. 여기에는 `visibility: 'public'` 필터가 없습니다 .
   반면 공개 목록용 엔드포인트 `community-memories.js`는 `visibility: 'public'` 필터를 명시하고 있어 설계 의도는 분명합니다 .
   이건 실제로 **public 트리 안의 private memory가 detail API에서 새어 나갈 수 있는 구조**라서 우선순위가 가장 높습니다.

2. **메모리 수정 API가 “받는 필드”와 “실제로 저장하는 필드”가 다름**
   `memory-detail.js`는 `source`, `sourceUrl`, `sourceType`, `thumbnail`, `timestamp`, `parentId`, `emotionTags`까지 수정 가능하다고 받아들입니다 .
   그런데 실제 DB update 함수 `updateMemory()`는 `title`, `memo`, `artist`, `visibility`만 업데이트합니다 .
   즉 프론트에서는 수정 성공처럼 보여도, 많은 필드가 **조용히 반영되지 않는 silent failure**가 날 수 있습니다.

3. **배포 전 검증 스크립트 신뢰도 낮음**
   `scripts/pre-deploy.js`는 `verifyFull()`에서 `execSync`를 사용하지만 import가 없습니다. 그대로면 런타임 에러가 납니다 .
   그리고 이 저장소의 README/기준 문서는 `src/*` 중심 구조를 강하게 설명하는데 , 실제 현재 페이지는 `pages/*.html` + `js/*`를 로드하고 있습니다. 예를 들어 `pages/search.html`은 `../js/search.js`, `../js/postgres-client.js` 등을 사용합니다 .
   즉 **문서/검증/실제 코드가 서로 다른 시대의 구조를 동시에 가리키고 있는 상태**입니다.

4. **XSS 방어가 약한 렌더링 코드가 있음**
   `js/search-card-renderer.js`는 `tree.title`, `mem.title`, `mem.thumbnail`, `tag` 등을 HTML 문자열에 직접 꽂아서 `innerHTML`로 렌더링하는 구조입니다 .
   `js/search-preview-renderer.js`도 `tree.title`, `firstMem.sourceUrl`, `firstMem.title`, `tree.theme` 등을 그대로 HTML/iframe src에 넣습니다 .
   반면 `js/auth/auth-ui.js`는 `escapeHtml()`을 따로 두고 사용자 이름/사진 URL을 이스케이프합니다. 즉 팀 내부에도 안전 패턴은 이미 있는데, 검색/미리보기 쪽에 일관되게 적용되지 않았습니다 .

5. **인증 토큰을 localStorage에 캐시**
   `js/postgres-client.js`는 Firebase ID token을 `lovebud_auth_token` 키로 localStorage에 저장합니다 .
   이 방식은 구현은 편하지만, 프론트 XSS가 한 번만 나도 토큰 탈취로 이어질 수 있어서 위의 렌더링 이슈와 합쳐지면 위험도가 커집니다.

좋았던 점도 있습니다.

* API 레이어를 `trees`, `memories`, `community-*`로 나눠 놓은 건 깔끔합니다 .
* DB 쿼리는 문자열 결합이 아니라 파라미터 바인딩을 써서 SQL injection 측면은 비교적 양호합니다 .
* 인증이 필요한 엔드포인트는 `requireUser()`를 일관되게 거치려는 방향이 보입니다  .

우선순위로 정리하면 이렇습니다.

* **P0**: `tree-detail.js`에서 public tree 조회 시 memory visibility 필터 추가
* **P0**: `updateMemory()`가 실제 허용 필드를 모두 업데이트하도록 수정
* **P1**: 검색/미리보기 렌더러의 HTML 문자열 삽입부 전부 escape 또는 DOM API 기반으로 변경
* **P1**: `pre-deploy.js` 고치고, 현재 실제 구조 기준으로 검증 항목 재정의
* **P2**: 문서(`README`, `FILE_BASELINE`)를 현재 코드 구조와 맞게 정리
* **P2**: localStorage 토큰 캐시 재검토
