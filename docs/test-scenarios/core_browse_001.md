# CORE-BROWSE-001

이 문서는 공개 트리 둘러보기에서 detail 보기로 이어지는 감상 흐름을 검증하는 현재 대표 시나리오입니다.

목적은 비로그인 또는 일반 탐색 사용자가 browse/search 화면에서 공개 러브트리를 보고, preview를 확인하고, detail로 이동한 뒤 다시 browse로 돌아오는 흐름이 자연스러운지 확인하는 것입니다.

---

## 1. 왜 중요한가

Browse는 제품의 공개 쇼케이스 역할을 합니다. 이 흐름이 좋아야 로그인 전에도 LoveTree의 감상 가치를 이해할 수 있습니다.

핵심은 다음입니다.
- 공개 러브트리가 실제로 browse에 보이는가
- 카드와 preview 정보가 탐색 판단에 충분한가
- preview 메모리가 비어도 fallback이 어색하지 않은가
- detail에서 트리/순간 맥락이 이해되는가
- 뒤로가기 후 다시 탐색이 이어지는가

---

## 2. 범위

### 대상 페이지
- search (둘러보기)
- detail

### 핵심 질문
- 공개 트리 탐색이 직관적인가
- 카드, preview, detail 정보가 서로 일관적인가
- 공개 트리지만 preview 또는 대표 메모리가 빈 경우 fallback이 자연스러운가
- empty state가 잘못 뜨지 않는가
- browse에서 detail로 갔다가 다시 돌아오는 흐름이 안정적인가

---

## 3. 사전 준비

- 공개 트리가 최소 1개 이상 존재해야 한다.
- 가능하면 메모리가 충분한 공개 트리 1개와 preview 정보가 빈약한 공개 트리 1개를 준비한다.
- 결과 폴더 권장 형식: `docs/test-scenarios/results/core-browse-001-{group}-YYYY-MM-DD-HHMM/`

---

## 4. 단계

### STEP 1. search 첫 인상
행동:
- 비로그인 상태 또는 일반 탐색 상태에서 search 화면에 진입한다.

기대 결과:
- 공개 러브트리를 감상하는 페이지라는 점이 이해된다.
- 카드 목록, 검색창, 필터, preview 영역의 역할이 구분된다.
- 공개 트리가 존재하는데 전체 empty state가 잘못 뜨지 않는다.

기록 항목:
- 첫 인상
- 목적 이해도
- empty state 오작동 여부

### STEP 2. 공개 트리 카드 확인
행동:
- 카드 목록을 훑고, 공개 러브트리가 실제로 렌더링되는지 확인한다.

기대 결과:
- 카드 제목, 썸네일, 감정 태그, 메모리 수 등 핵심 정보가 보인다.
- 공개가 아닌 데이터가 섞여 보이지 않는다.
- 카드가 지나치게 비거나 placeholder처럼 느껴지지 않는다.

기록 항목:
- 카드 정보 충분성
- 썸네일/태그 fallback 자연스러움
- 이상 카드 여부

### STEP 3. 검색/필터 반응 확인
행동:
- 검색어를 입력하거나 필터를 바꿔본다.

기대 결과:
- 검색/필터 적용 결과가 자연스럽게 바뀐다.
- 결과가 없을 때는 검색 empty state가 뜨고, 전체 데이터가 있는 상황에서는 전역 empty state와 혼동되지 않는다.
- 전체/검색 결과/필터 결과의 상태 구분이 명확하다.

기록 항목:
- 필터 이해도
- 결과 전환 자연스러움
- empty state 혼선 여부

### STEP 4. preview 확인
행동:
- 카드 hover 또는 선택으로 preview를 확인한다.

기대 결과:
- preview가 detail 진입 전에 도움이 된다.
- 카드 정보와 preview 정보가 서로 충돌하지 않는다.
- 대표 메모리나 preview 메모리가 부족해도 fallback 문구나 미리보기 상태가 깨지지 않는다.

기록 항목:
- preview 유용성
- 카드/preview 일관성
- 빈 preview fallback 자연스러움

### STEP 5. 공개 트리 detail 진입
행동:
- 공개 트리 하나를 선택해 detail로 이동한다.

기대 결과:
- 이동이 빠르고 자연스럽다.
- detail에서 지금 보고 있는 것이 트리인지, 순간인지, 연결된 기억인지 구분된다.
- 대표 메모리나 연결 데이터가 부족해도 null/empty UI가 어색하지 않다.

기록 항목:
- 이동 결과
- detail 이해도
- fallback 자연스러움

### STEP 6. preview 빈약 트리 또는 대표 메모리 부족 케이스 확인
행동:
- preview 정보가 약하거나 대표 메모리가 빈약한 공개 트리를 골라 같은 흐름을 다시 본다.

기대 결과:
- preview가 비어도 전체 browse가 깨지지 않는다.
- 카드/preview/detail 어느 단계에서도 잘못된 전역 empty state가 뜨지 않는다.
- fallback 문구가 차갑거나 시스템적이지 않고, 최소한의 맥락을 유지한다.

기록 항목:
- fallback 문구 품질
- empty state 오작동 여부
- 가장 어색한 지점 1개

### STEP 7. browse로 복귀
행동:
- detail에서 뒤로가기를 하거나 browse로 돌아간다.

기대 결과:
- 이전 탐색 상태가 크게 깨지지 않는다.
- 검색어/필터/스크롤 위치가 완전히 초기화되더라도 사용자가 다시 탐색을 이어가기 어렵지 않다.
- 복귀 직후 카드나 preview가 잘못된 빈 상태로 보이지 않는다.

기록 항목:
- 복귀 안정성
- 탐색 연속성
- 상태 유지 여부

---

## 5. 에지 체크

- 검색 결과가 적을 때도 카드/preview 레이아웃이 어색하지 않은가
- 대표 썸네일이 비어도 fallback이 자연스러운가
- detail 직접 진입과 browse 경유 진입의 degraded/fallback 차이가 과도하지 않은가
- 공개 트리가 있는데 browse 전체 empty state가 뜨는 경우가 없는가

---

## 6. 최종 판정

통과:
- 공개 러브트리가 browse에 실제로 보이고, preview와 detail까지의 감상 흐름이 자연스럽다.
- preview 또는 대표 메모리 부족 케이스에서도 fallback과 empty state가 안정적이다.

조건부 통과:
- 탐색은 가능하지만 카드/preview/detail 연결이 다소 어색하거나 fallback 문구가 건조하다.

실패:
- 공개 트리가 있는데 browse에 보이지 않거나, 잘못된 empty state가 뜨거나, preview/detail 진입 흐름이 크게 깨진다.
