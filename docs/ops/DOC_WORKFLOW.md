# LoveBud 문서 작업 흐름

## 목적

이 문서는 LoveBud 문서를 왜 만들고, 어떻게 대화에서 문서로, 문서에서 구현으로 이어갈지 정리합니다.

핵심 목적은 단순 기록이 아니라 **사이트를 더 잘 만들기 위한 설계 기준 축적**입니다.

---

## 기본 원칙

1. 대화는 아이디어를 흘려보내지 않고 문서 기준으로 남긴다.
2. 문서는 기록용이 아니라 구현 기준으로 쓴다.
3. 페이지 문서는 UI만이 아니라 기능, 상태, 데이터, 백엔드 연결까지 포함한다.
4. 구현은 가능한 한 문서 기준이 선명해진 뒤 진행한다.
5. 원문 기록과 정제 문서의 역할을 섞지 않는다.

---

## 작업 흐름

### 1. 대화

사용자와 모델이 페이지, 기능, 백엔드, 운영 이슈를 대화로 정리한다.

이 단계의 목표:
- 문제를 넓게 본다
- 빠진 관점을 찾는다
- 확정 / 제안 / 미정 사항을 구분한다

### 2. 대화 기록 보존

대화 원문은 필요 시 `docs/conversation/full/`에 보존한다.

보존 원칙:
- 원문은 원문대로 유지
- 파일명은 본문 대표성 있게 정리
- summary를 별도로 생성

### 3. 정제 문서 반영

대화에서 확정된 내용은 아래 문서군에 반영한다.

- 페이지 관련: `docs/pages/`
- 제품 방향: `docs/product/`
- 백엔드/API/데이터: `docs/backend/` 또는 `docs/backend.md`
- 운영 규칙: `docs/ops/`

이 단계의 목표:
- 다음 세션이 와도 바로 이어갈 수 있게 함
- 구현 전에 기준을 선명하게 함

### 4. 구현

구현 모델은 conversation 원문보다 **정제 문서**를 우선 기준으로 삼는다.

즉:
- `conversation`은 근거
- `pages/product/backend/ops` 문서는 실행 기준

### 5. 검증 후 문서 보정

구현 후에는 실제 코드 상태와 문서가 어긋나지 않도록 다시 반영한다.

---

## 문서군 역할

### `docs/conversation/`

- 세션 기록
- raw transcript
- summary
- handoff / derived 문서

질문:
- "우리가 무슨 대화를 했나?"

### `docs/pages/`

- 페이지별 목적
- 주요 UI 블록
- 핵심 기능
- 사용자 행동
- 상태 변화
- 필요한 데이터/API
- 리스크 / 다음 작업

질문:
- "이 페이지는 무엇을 해야 하나?"

### `docs/product/`

- 서비스 정체성
- 제품 범위
- MVP 기준
- 사용자 흐름

질문:
- "이 서비스는 무엇을 만들고 있나?"

### `docs/backend/` / `docs/backend.md`

- API 역할
- 데이터 모델
- 인증/권한
- 함수 구조
- 페이지와의 데이터 연결

질문:
- "이 기능을 위해 서버/DB는 무엇을 제공해야 하나?"

### `docs/ops/`

- 작업 환경
- 경로/셸
- 배포
- 문서 및 운영 규칙

질문:
- "이 프로젝트를 안정적으로 운영하려면 무엇을 알아야 하나?"

## 인덱스 파일명 규칙

LoveBud 문서군의 인덱스 파일명은 일반적인 `index.md` 가 아니라 **`폴더명_index.md`** 를 기본으로 사용합니다.

예:
- `pages_index.md`
- `product_index.md`
- `ops_index.md`
- `reports_index.md`
- `plans_index.md`
- `archive_index.md`
- `design_index.md`

예외:
- 최상위 문서 인덱스는 `docs/doc_index.md`
- conversation 하위는 기존 관례대로 `full_index.md`, `summary_index.md`

따라서 새 폴더 인덱스를 만들 때는 먼저 해당 폴더의 기존 네이밍 관례를 확인하고,
관례가 없으면 `폴더명_index.md`를 사용합니다.

## 페이지 문서 원칙

페이지 문서는 UI 설명서가 아닙니다.

반드시 함께 다뤄야 할 항목:
- 페이지 목적
- 사용자 목표
- 핵심 UI 구성
- 기능
- 상태별 동작
- 필요한 데이터
- 백엔드/API 연결 포인트
- 미정 사항

즉 페이지 문서는 `화면`과 `기능`을 함께 다룹니다.

---

## 백엔드 문서 원칙

백엔드 문서는 서버 코드 설명이 아니라, **프론트가 필요로 하는 데이터와 동작을 명확히 하는 문서**여야 합니다.

우선순위:
1. 어떤 페이지가 어떤 데이터를 필요로 하는가
2. 어떤 API/함수가 그 요구를 충족하는가
3. 인증/권한은 어디서 검사되는가
4. 현재 구현 상태와 미구현 범위가 무엇인가

---

## 대화 시 권장 질문

페이지/기능 대화에서는 아래 질문을 기준으로 좁혀간다.

- 이 페이지의 가장 중요한 사용자 행동은 무엇인가?
- 이 행동을 위해 화면에 반드시 있어야 할 요소는 무엇인가?
- 사용자가 성공/실패/빈 상태에서 무엇을 보게 되는가?
- 이 페이지가 필요로 하는 데이터는 무엇인가?
- 그 데이터는 어디서 오며, 백엔드는 무엇을 해야 하는가?
- 지금 확정된 것과 아직 미정인 것은 무엇인가?

---

## 현재 MVP 우선순위

로드맵 기준으로 현재 다음 작업 우선순위는 아래와 같다.

1. `editor` 편집/삭제 개선
2. `home` 역할 및 랜딩 개편
3. UI 상태 문서화
4. DB/API 문서화

즉 현재 MVP 기준으로는 **editor가 첫 번째 상세 설계/구현 우선순위**다.

---

## 운영 메모

- 빠른 모델과는 대화 중심으로 페이지/기능/백엔드 판단을 정리한다.
- 정리된 내용은 이후 문서 반영용 모델에게 넘겨 `docs/pages/`, `docs/backend/`, `docs/product/` 등에 반영한다.
- 문서가 기준이 되고, 구현은 그 문서를 따라가도록 운영한다.
